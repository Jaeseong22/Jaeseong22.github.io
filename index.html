공시 Agent

역할

Agent의 설계와 구현, 서버 배포를 전담했고, 구현에는 Claude를 활용했습니다. 프론트엔드 디자인은 다른 팀원이 맡았습니다.

문제

공시 답변은 숫자 하나만 틀려도 전체를 믿을 수 없습니다. 70개 기업, 5.2GB 분량의 공시 원문을 LLM에게 그대로 읽히면 그럴듯한 오답이 나올 위험이 컸습니다.

핵심 결정

  1. 계산은 코드에, 판단은 LLM에표 추출, 재무 수치 조회, 계산은 결정론적 도구로 만들었습니다. LLM은 어떤 도구를 어떤 인자로 부를지 정하고 결과를 서술하는 일만 맡습니다.
  2. 도구는 12개까지도구가 늘어날수록 LLM의 도구 선택 정확도가 떨어지기 때문에 상한을 정해 두었습니다.
  3. 모르면 답하지 않는다표를 확정하지 못하면 값을 내지 않고(fail-closed), 도구 근거 없이 사실을 주장하는 답변은 출력 관문에서 차단했습니다.

결과

정본표 2,380건과 정형공시 3,150건을 캐시로 구축해 모든 답변에 공시 접수번호를 근거로 붙였습니다. 프롬프트 공격 테스트 6건을 모두 차단했고 지시 유출은 40회 중 0회였습니다. 2 vCPU · 4GB 서버에 nginx와 systemd로 배포해 평가용 API로 운영했습니다.

경비 판정 서비스

문제

같은 지출이라도 업종, 매출, 직원 유무에 따라 경비로 인정되는지가 달라집니다. 하지만 1인 사업자는 자기 기준을 확인할 방법이 없습니다. 판정은 검수를 마친 규칙 카드를 순서대로 실행하는 규칙 엔진이 내리고, 판정 경로에서 LLM은 가맹점 분류까지만 맡습니다.

내가 한 일

  1. 디자인 시스템색과 타이포 토큰, 공용 부품 11종을 규칙 문서와 함께 정리해 팀원 누구나 같은 화면을 만들 수 있게 했습니다.
  2. API 레이어API 명세와 1:1로 대응하는 요청·응답 타입 계약 29개를 두어, 목업과 실제 서버를 한 줄로 바꿔 끼울 수 있게 만들었습니다.
  3. 업로드부터 판정까지의 화면가맹점 분류 확인, 거래 목록, 업로드 이력, 사업자 문진, 판정 확인, 그리고 부분 실패와 재시도를 포함한 판정 진행률 화면을 구현했습니다.

fin_agent

문제

"두 종목의 최근 3개월 수익률을 비교해줘", "RSI 70을 돌파한 종목은?" 같은 질문은 형태가 제각각이고, 조건이 빠지거나 모호한 경우가 많습니다. 빠진 조건을 LLM이 추측해 채우면 틀린 숫자가 그대로 답이 됩니다.

핵심 결정

  1. 질문을 네 갈래로 나눈다단순 조회·랭킹, 조건 검색, 신호·패턴 탐지, 일반 대화로 분류해 경로마다 다른 파싱 프롬프트와 SQL을 쓰게 했습니다.
  2. 모르면 되묻는다필수 조건이 빠지면 LangGraph interrupt로 그래프를 멈추고 빠진 항목만 묻습니다. 사용자가 답하면 원래 질문과 합쳐 다시 분류합니다.
  3. 실패를 질문으로 바꾼다파싱 결과는 Pydantic으로 검증하고 필수 조건을 확인한 뒤에만 DB를 조회합니다. 검증 실패는 오류 대신 질문으로, 분류 실패는 챗봇으로 넘깁니다.
